# SILONG

**Urban Heat Risk Intelligence Platform**

SILONG combines weather, population, environmental-data interfaces, and geospatial analytics to explore heat exposure across Metro Manila. It provides interactive mapping, historical analysis, population co-location estimates, retrospective forecasts, and transparent scenario simulation.

The active application uses **real 2025 ERA5-Land reanalysis and official PSA 2020 census counts**, not synthetic weather. Reanalysis is historical model output informed by observations, not a local weather-station measurement. Missing environmental layers remain missing.

## Overview

Next.js/TypeScript frontend; modular Python/FastAPI analytics; optional PostgreSQL/PostGIS. The bundled, offline-capable browser dataset is generated by the same Python pipeline used by the API. No private API key is needed for public exploration.

## Problem Statement

City-level weather and population need to be examined together without confusing exposure, individual vulnerability, and official alerts. SILONG exposes provenance, geographic resolution, data vintage, and model assumptions alongside its results.

## Research Questions

- How do historical heat-index patterns vary by hour and month?
- Which sampling locations repeatedly exceed configured screening thresholds?
- How much historical census population is associated with those city categories?
- Can recent weather predict subsequent heat-index estimates in a chronological test?
- Which environmental questions remain unsupported by the available data?

## Key Features

- All 17 NCR locations, source PSGC identifiers, offline Leaflet boundary map, zoom/pan, hover, detail panels, metric layers, and keyboard-accessible location lists.
- Location/date/hour filtering, hourly-to-yearly trends, daily heat calendar, scatter plots, descriptive statistics, city comparison, hotspot frequency, and filtered CSV export.
- 6/12/24-hour retrospective forecasts; persistence/linear/random-forest/gradient-boosting comparison; measured MAE/RMSE/R² and classification metrics; permutation importance; empirical intervals and coverage.
- Temperature/humidity/population scenarios with baseline comparison. Environmental controls are disabled until verified inputs exist.
- Warm atmospheric light and dark themes, persistent theme preference, collapsible navigation, mobile drawer, skeletons, error/empty states, and public anonymous access.
- Admin-token protected CSV/GeoJSON preview and candidate staging. Uploads cannot silently replace the active dataset.

## Data Pipeline

Raw response → unit/time validation → cleaning → heat-index calculation → city-ID join → analytics/features → chronological models → API/export → dashboard.

Required missing observations, invalid timestamps, unknown IDs, temperature outside 10–50°C, and humidity outside 0–100% are rejected. Duplicate city/time pairs retain the final row. Six-MAD outliers are flagged and retained. Missing hours are excluded from forecast windows. No interpolation or synthetic backfill occurs.

## Data Science Workflow

The Python pipeline calculates summary distributions, hourly/monthly means, city means and maxima, elevated-hour shares, weekly changes, and descriptive Pearson/Spearman relationships. City samples sharing a grid are dependent: nominal p-values do **not** support independence-based significance claims. One year cannot establish a long-term warming trend.

## Machine Learning

Training: January–September 2025; validation: October–November; untouched test: December. Both origin and target stay in their split. Models use every sixth row of sorted city series to control training cost; no random time-series split occurs.

Current/recent temperature, humidity, heat index, trailing means, and cyclic time terms predict direct 6/12/24-hour targets. Model-family selection minimizes mean validation MAE across horizons. The saved registry includes test metrics, validation metrics, features, periods, version, training timestamp, and empirical interval coverage. Forecasts are anchored to the dataset endpoint, **not today**.

Classification metrics can be uninformative when a test slice contains only one analytical category; consult regression errors and the configured thresholds. The intervals use validation absolute residuals and are not guaranteed real-world confidence bounds. Only application-generated joblib artifacts may be loaded; do not accept uploaded pickle/joblib files.

## Simulation Engine

The active real-data mode recalculates weather-derived heat index under hypothetical temperature/RH changes. Population-density changes scale historical census population at fixed area. Threshold crossing reassigns the whole city population; this is not an estimate of people helped by an intervention.

Vegetation and built-up baselines are unavailable, so those controls are disabled and the API rejects unsupported environmental changes. No causal cooling coefficient is assumed.

## Methodology

Heat index follows the [NWS Rothfusz procedure](https://www.wpc.ncep.noaa.gov/html/heatindex_equation.shtml), including preliminary formula and humidity adjustments. It assumes shade/light wind.

The original four-component Urban Heat Exposure Index cannot be calculated honestly without environmental inputs. The active **heat-only screening** measure is:

```text
100 × clip((calculated heat index in °C − 27) / 27, 0, 1)
```

Its configurable score bands are exploratory, not official classifications. Population density is independent context and is not secretly assigned a replacement weight. The full original demo configuration remains in `config/methodology.demo.json`. `config/methodology.json` is the sole active Python/browser configuration source.

## Installation

Prerequisites: Python 3.12, Node.js 22+, npm. Docker is optional for PostgreSQL.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.lock.txt
npm.cmd --prefix frontend ci
```

On macOS/Linux, use `.venv/bin/python` and `npm`. `backend/requirements.txt` describes supported ranges; the lock captures the tested environment. Windows application control may restrict native projection DLLs; the RFC 7946 geographic join avoids GDAL/projection dependencies because no reprojection is needed. Raster and arbitrary-CRS ingestion require a fully configured geospatial runtime.

## Running Locally

Browser-only real-data dashboard (works immediately from bundled files):

```powershell

```

API with trained inference (separate terminal):

```powershell
.\.venv\Scripts\python.exe scripts/train_models.py
.\.venv\Scripts\python.exe -m uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

To connect the frontend to the Python API, put `NEXT_PUBLIC_API_URL=http://127.0.0.1:8000` in `frontend/.env.local` and restart Next.js. API failures are shown rather than silently switching datasets. Interactive OpenAPI docs: `http://127.0.0.1:8000/docs`.

The export script name is retained for compatibility; it exports the **active real dataset**. Ingestion uses the cached raw response when present and refuses incomplete data. Optional `scripts/generate_demo.py` writes only to `backend/data/demo/` and cannot overwrite the active real dataset.

## Model Training

`scripts/train_models.py` recreates the models and registry. Artifacts are named by dataset version, preventing an old synthetic artifact from serving the real dataset. After training, rerun the export script to refresh browser predictions. Changing weights, data, or feature definitions requires retraining/re-export and review.

This environment had no Docker/PostgreSQL executable, so live database execution was not verified here; the default file-backed app and API were tested.

## API

`GET /api/dataset`, `/api/overview`, `/api/locations`, `/api/locations/{id}`, `/api/heat/trends`, `/api/exposure`, `/api/hotspots`, `/api/forecast`, `/api/analytics`, `/api/data-quality`, `/api/model/metrics`, `/api/methodology`; `POST /api/simulation`; authenticated `/api/import/preview` and `/api/import/commit`.

Dates are ISO dates and hours are PHT. Forecast horizons are 6, 12, or 24. Uploads are capped at 5 MB. Commit verifies the preview SHA-256 and revalidates the file; validated candidates are stored separately with `pending-review` and `unverified-upload` status. Activating a new source is a developer review workflow, not an automatic public action.

## Deployment

- **Vercel:** set project root to `frontend`, use `npm run build`, output `out`. This is a Next.js static export. Set `NEXT_PUBLIC_API_URL` before building if using the Python backend.
- **Render / Railway / Fly:** build `backend/Dockerfile` from the repository root. It installs dependencies and trains the versioned model; expose port 8000. `render.yaml` supplies a starting blueprint. Configure CORS and secrets in the host.
- **PostgreSQL/PostGIS:** host separately, run migrations/seed, set `DATABASE_URL` on the backend. Use production credentials and TLS per provider requirements.
- **Static demo hosting:** the exported frontend includes real data and precomputed forecasts, so exploration works without a separately deployed API. Admin import requires the configured backend.

## Limitations

Six weather grids cannot resolve 17 independent urban microclimates. Population and geometry vintages differ, and Makati/Taguig administrative changes require explicit reconciliation before current-boundary analysis. Environmental layers are missing; full composite scoring is disabled. Forecasts are retrospective experiments on reanalysis. Shared grids, one-year coverage, sampling, and uncalibrated screening bands limit inference.

## Future Improvements

Verified PAGASA station validation, reconciled contemporary census/boundary geography, licensed vegetation/built-up rasters, spatially independent validation, longer weather histories, calibrated screening criteria, data-version activation UI, and a verified PostGIS deployment.

## Disclaimer

SILONG provides analytical estimates, not official government warnings or individual health-risk assessments. Reanalysis, census, calculated, predicted, simulated, and unavailable data are labeled separately. No synthetic values are used to fill gaps in the active dataset.
